# SQLite 存储热点优化

本轮在 `bb602e1` 的按类型拆表基础上修复索引退化，并降低脱敏、历史替换、历史计数和重新打开数据库的成本。HTTP、工具协议和消息格式不变。

## 查询与写入

- `effects.projectId` 和 `runId` 保留完整表达式索引。状态索引只覆盖业务恢复使用的 `running`、`prepared`，终态写入不再维护状态索引。Store 对这些状态的筛选会带上等价的固定谓词以使用部分索引；其他状态筛选仍正确，但不带 runId/projectId 的终态查询会扫描 effects 表。
- 固定实体类型的读写、删除和计数复用预编译语句。通用查询与 JSON 查询各有 128 项语句上限，固定实体语句最多为实体类型数乘以四；不缓存实体记录或权限结果。
- 支持 `StatementSync.setReturnArrays` 的 Node 运行时内部使用数组行读取 JSON，减少对象构造；不支持时继续读取命名行。内部 JSON 语句与公开 `Store.prepare()` 的语句分开，公开调用的命名列格式不变。
- 项目预算使用覆盖索引，直接累计索引中的计费表达式值，避免逐条读取并解析费用 JSON。费用表用 `seq INTEGER PRIMARY KEY` 显式命名原来的 rowid，覆盖索引按项目、seq、日期和计费表达式排列，同时支持费用列表的插入顺序；因此可以移除重复的项目单字段索引，减少写入维护，列表不需要额外排序。session、run 和日期索引保留。
- 旧费用表在事务中升级，复制原有 rowid，保留自定义索引及触发器；写事务内一次完成 schema 的补建，避免逐条 DDL 提交。SQLite 在写入和原始 SQL 更新时自动维护表达式索引；金额溢出、未结算、未知、作废和缺失实付金额的语义保持一致。
- 固定类型缓存写入函数及序列化方式，减少每行写入重复的类型查找和分支；每次脱敏写入仍读取当前凭据快照。

## 页缓存与提交

保留原有 4 KiB 页布局及 WAL、FULL 同步。每个连接的 SQLite 页缓存上限设为 8 MiB，减少批量写入过程的缓存换出；缓存按实际使用分配，不缓存应用记录或权限结果。较大的数据页会增加逐条提交的 WAL 帧字节数，8/16 KiB 页实验因此未采用。

## 脱敏与历史替换

每次独立操作仍重新读取已注册凭据及当前凭据环境变量，保留新增、轮换、删除与过期行为。环境变量先枚举名称，只读取名称匹配凭据规则的值，避免 Windows 下读取全部环境变量值的成本；重复的凭据值只检查一次。

一次同步 `saveTranscript` 复用同一个脱敏上下文，每条输入消息只序列化一次。先检查重复消息 ID 与内容冲突，再保留完全相同的历史前缀，删除和插入变化后缀。后缀身份已在同一次事务内验证，不再逐条先查询再插入。新的保存、追加、实体写入和事件操作会重新建立自己的脱敏上下文。

## 精确的历史计数

`transcript_counts` 是 SQLite 内部派生表，保存每个会话的精确消息数量。消息插入、删除和会话归属更新通过三个数据库触发器维护计数，与消息变更处于同一事务。Store 连接启用 `recursive_triggers`，使 `REPLACE` 的隐式删除也正确更新计数；`IGNORE` 不改变计数。Store 连接上的原始 SQL、跨 Store 连接、嵌套事务和回滚同样生效；分页不再每次扫描全部会话消息来计算总数。额外的外部 SQLite 写连接同样需要启用 `recursive_triggers`。

首次升级在写事务内从既有消息回填计数并登记迁移 5。计数表或其触发器缺失时重新回填并修复。计数维护会增加少量派生行更新，特别是批量替换历史时；性能报告区分消息行与计数维护的总变更数。

## 打开与修复

打开数据库时读取一次实际 schema 名称，只为缺失的实体表或索引执行 DDL。旧 `entities` 拆表迁移仍在事务中运行；缺失索引修复与未知类型保留的行为不变。消息计数对象同样根据实际 schema 检查，修复不依赖进程内的历史状态。

WAL、同步级别、外键和忙等待配置保持原有设置；本轮没有降低提交的持久性要求。

## 验证与证据

`test/storage-performance.test.ts` 覆盖项目筛选索引及其修复、项目费用覆盖索引、历史前缀与冲突回滚、凭据轮换、跨连接计数、原始 SQL 的会话移动、触发器修复，以及 JSON 读取与公开命名列的兼容性。

与 `bb602e1` 的原版编译结果使用相同确定性数据、相同工作量和交替顺序重新测量。正式结果保存在本地 `verification/sqlite-tuning-bb602e1-20261022/`；每个场景同时保留前后各轮耗时及波动区间。此前与父提交的对比保存在 `verification/sqlite-performance-bb602e1-20261022/`，两次实验分别报告。

后续写入修复使用快速定向流程：

```powershell
npm run test:storage
npm run bench:storage
```

前者仅执行存储、查询和费用相关测试，跳过无关测试文件的转译；后者只转译 Store 的运行时依赖，将 HEAD 与当前源码快照作七轮交替比较。每版只生成一份夹具并复用，测量十个写入及读取保护场景，不重复完整历史替换或模型、网络测试。默认输出到 `verification/storage-write-benchmark/quick-benchmark.json`。可用 `--ref` 指定原始提交，`--previous-dist` 增加上一版的编译目录，`--output` 指定结果目录；快速结果与此前独立进程的完整结果分开保存。波动区间跨 1× 时按测量不确定性展示，不把微小点估计直接判为退化。
